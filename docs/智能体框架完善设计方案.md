## 2. OfficeCLI 集成方案

### 2.1 OfficeCLI 简介

[OfficeCLI](https://github.com/iOfficeAI/OfficeCLI) 是全球首个专为 AI 智能体设计的命令行工具：

- **单一二进制文件**：内嵌 .NET 运行时，零依赖，全平台运行
- **三格式全覆盖**：Word (.docx)、Excel (.xlsx)、PowerPoint (.pptx)
- **三层架构**：L1 语义视图 → L2 DOM 操作 → L3 原始 XML
- **AI 原生**：所有命令支持 `--json` 输出，基于路径的元素寻址
- **内置 MCP Server**：支持 Claude Code、Cursor、VS Code 等
- **SKILL.md 机制**：自带技能文件，AI 可自动学习使用
- **Apache 2.0 开源**

### 2.2 与现有技能系统对比

```
现有方案（Python Skills）          OfficeCLI 方案
─────────────────────          ─────────────────
python-docx + openpyxl    →    officecli 单一二进制
python-pptx + pandas      →    officecli 统一 CLI
需要 Python 环境          →    无依赖，直接调用
每个 Skill 单独维护       →    一个工具覆盖三格式
XML 解析容易出错          →    路径寻址，结构化 JSON
需要 Pyodide 运行时       →    BashTools 直接执行
```

## 3. 文件拖拽与工具推荐

### 3.1 核心设计原则：延迟读取（Lazy Loading）

**不预提取文件内容，仅注入元信息 + 工具推荐，由 AI 自行决定何时、如何读取文件。**

```
❌ 旧思路（预提取）：
   用户拖入 3 个文件 → 全部提取内容 → 注入消息 → 上下文爆满

✅ 新思路（延迟读取）：
   用户拖入 3 个文件 → 仅注入元信息+推荐工具 → AI 按需调用工具读取
```

| 文件类型 | 注入到消息的内容 | 推荐工具 |
|----------|-----------------|----------|
| 图片 (.png/.jpg/.gif/.webp) | base64 多模态数据（由视觉模型直接处理） | 模型原生视觉能力 |
| 文本 (.txt/.md/.json/.csv/.yaml) | 文件路径 + 大小 + 编码 | `read_file` |
| 代码 (.ts/.js/.py/.java/.go) | 文件路径 + 大小 + 语言 | `read_file` |
| Word (.docx) | 文件路径 + 大小 | `office_view` / `office_get` |
| Excel (.xlsx) | 文件路径 + 大小 + 工作表数 | `office_view text` |
| PowerPoint (.pptx) | 文件路径 + 大小 + 页数 | `office_view outline` |
| PDF (.pdf) | 文件路径 + 大小 + 页数 | `read_file`（或专用 PDF 工具） |

### 3.3 文件处理流程

```
文件拖入/选择
  │
  ├─ 1. 文件保存到工作空间
  │     .config/data/workspaces/sessions/{id}/attachments/{filename}
  │
  ├─ 2. 收集文件元信息（仅此步，不读内容）
  │     ├── 文件名、扩展名、大小
  │     ├── MIME 类型
  │     └── Office 文档：页数/工作表数（通过 officecli view stats，仅元信息）
  │
  ├─ 3. 根据类型生成工具推荐提示
  │     参见 3.4 消息注入格式
  │
  └─ 4. 图片特殊处理

        但控制单张图片最大尺寸，过大则缩放
```

### 3.4 消息注入格式

发送消息时，将文件信息以结构化方式追加到用户消息末尾。AI 据此判断该用哪个工具读取文件：

```markdown
用户输入：请帮我分析这份报告

---
📎 用户提供了以下文件：

| # | 文件名 | 类型 | 大小 | 推荐读取方式 |
|---|--------|------|------|-------------|
| 1 | Q4季度报告.docx | Word 文档 | 2.3 MB | 使用 `office_view` 查看大纲，`office_get` 读取具体章节 |
| 2 | 销售数据.xlsx | Excel 表格 | 1.1 MB，3个工作表 | 使用 `office_view text --cols A,B,C` 查看数据 |
| 3 | 架构图.png | 图片 | 500 KB | 已内嵌，可直接查看 |

路径：{workspace_path}
请根据需要使用相应工具读取文件内容。
```

实际注入代码逻辑：

```typescript
// 文件类型 → 工具推荐映射
const TOOL_RECOMMENDATIONS: Record<string, string> = {
  image: "已内嵌，可直接查看",                          // 图片走多模态
  text:   "使用 read_file 读取全文",
  code:   "使用 read_file 读取源码",
  docx:   "使用 office_view 查看大纲，office_get 读取具体段落",
  xlsx:   "使用 office_view text 查看数据，office_get 获取单元格",
  pptx:   "使用 office_view outline 查看结构，office_get 读取幻灯片",
  pdf:    "使用 read_file 读取文本内容",
  other:  "使用 read_file 尝试读取，或 get_file_info 查看详情",
};

function buildFileContext(files: FileInfo[]): string {
  if (files.length === 0) return '';

  const header = '📎 用户提供了以下文件：\n';
  const table = '| # | 文件名 | 类型 | 大小 | 推荐读取方式 |\n' +
                '|---|--------|------|------|-------------|\n';

  const rows = files.map((f, i) =>
    `| ${i+1} | ${f.name} | ${f.typeLabel} | ${formatSize(f.size)} | ${TOOL_RECOMMENDATIONS[f.category]} |`
  ).join('\n');

  return header + table + `\n\n路径：${files[0].dirPath}\n请根据需要使用相应工具读取文件内容。`;
}
```

### 3.7 模型能力检测与图片上传控制

#### 3.7.1 问题

当前系统无条件将图片以 OpenAI 多模态格式发送。如果用户使用的模型不支持视觉能力（如 GPT-3.5、部分本地模型），会导致 API 报错。需要：

1. 检测/标注模型是否支持视觉能力
2. 不支持时，拦截图片上传并给出提示
3. 提供降级方案：用图片描述工具替代多模态输入

#### 3.7.2 能力检测策略：自动探测 + 手动覆盖

```
模型配置保存/切换
  │
  ├─ 自动探测（优先）
  │   根据模型名称匹配已知能力表
  │   ┌─────────────────────────────────────────────────┐
  │   │ 支持视觉的模型关键词：                             │
  │   │ gpt-4o, gpt-4-turbo, gpt-4-vision              │
  │   │ claude-3, claude-sonnet, claude-opus, claude-3.5│
  │   │ gemini, qwen-vl, qwen2-vl, internvl            │
  │   │ glm-4v, yi-vision                               │
  │   │                                                  │
  │   │ 不支持视觉的模型关键词：                            │
  │   │ gpt-3.5, text-davinci, codellama                │
```

```typescript
    'deepseek-coder', 'deepseek-chat',

  // 负面匹配优先

  // 正面匹配
  if (VISION_KEYWORDS.some(k => name.includes(k))) {
    return { vision: true, toolUse: true, streaming: true };
  }

  // 未知模型：默认不支持视觉，用户可手动开启
  return { vision: false, toolUse: true, streaming: true };
}
```

```typescript
async function processAttachmentsInMessages(messages, config) {
  const capabilities = config.capabilities || detectCapabilities(config.model);

  for (const msg of messages) {
    if (msg.role !== 'user' || !msg.images?.length) continue;

    if (capabilities.vision) {
      // 模型支持视觉 → 正常转多模态格式
      msg.content = convertToMultimodal(msg.content, msg.images);
    } else {
      // 模型不支持视觉 → 图片降级为路径引用
      const imagePaths = msg.images.map((img, i) =>
        `[图片 ${i+1}: 已保存，当前模型无法查看]`
      ).join('\n');
      msg.content += '\n\n' + imagePaths;
      msg.images = [];  // 清空，不发送多模态数据
    }
  }
}
```

#### 5.3.2 总结触发时机

```
触发方式一：会话结束
  用户关闭/切换对话 → 检查消息数量 > 5 → 触发总结
  │
  │  优点：及时，上下文完整
  │  缺点：频繁调用 LLM，消耗 token

触发方式二：定时任务（推荐）
  每日 23:00 定时执行 → 收集当日所有已结束的会话 → 批量总结
  │
  │  优点：批量处理，节省 token
  │  缺点：有延迟

推荐方案：两者结合
  - 会话结束时标记为"待总结"
  - 定时任务批量处理"待总结"的会话
  - 超过 50 条消息的会话立即总结（避免丢失信息）
```

### 7.5 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|----------|
| OfficeCLI 二进制下载失败 | Office 功能不可用 | 保留 Python Skills 作为 fallback |
| AI 未正确使用推荐工具 | 文件内容未被读取 | 系统提示中明确引导：遇到文件先读取再回答 |
| 能力检测误判 | 支持视觉的模型被标记为不支持 | 手动覆盖开关兜底，用户可随时修正 |
| 图片过多导致上下文过大 | 多模态 token 消耗 | 单张图片最大 1MB（超过则缩放），最多 5 张 |
| 每日总结消耗过多 token | 成本增加 | 使用更小的模型（如 Haiku）进行总结 |
| 定时任务执行时应用未运行 | 任务丢失 | 记录待执行状态，启动时补执行 |
