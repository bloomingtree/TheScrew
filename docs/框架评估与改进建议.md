> 评估日期：2026-05-06（修订）
> 评估范围：模型适配层、Office 功能方案、工具/Skill 系统架构、整体工程质量
> 修订说明：经深入调研，推翻了初版中"继续使用 Skills 系统"的结论，改为推荐 OfficeCLI

## 一、Office 功能方案评估与决策

### 1.1 现状分析

当前项目中存在 **两套** Office 处理路径，互不兼容，且有部分重叠：

| 方案 | 状态 | 实现方式 |
|------|------|----------|
| **Skills 系统** (docx/xlsx/pptx) | 活跃使用中 | AI 读取 SKILL.md → 生成代码 → 通过 Bash 执行 Python/Node.js |
| **OfficeCLI Tools** | 代码已实现，但二进制未安装 | 10 个结构化工具，调用 `officecli` 二进制 |

### 1.2 Skills 系统的实际问题

经过深入代码审查，Skills 系统在实际使用中存在以下严重问题：

#### A. 依赖链过长，环境脆弱

| 依赖 | 用途 | 问题 |
|------|------|------|
| python-pptx | PPTX 生成/读取 | 需要安装到 embed Python |
| openpyxl | XLSX 读写/公式 | 同上 |
| defusedxml | DOCX XML 安全解析 | 同上 |
| pandas | XLSX 数据分析 | 体积大（~30MB） |
| LibreOffice (soffice) | 公式重算、修订接受、格式转换 | ~500MB，启动慢 |
| pandoc | DOCX 文本提取 | 额外安装 |
| Poppler (pdftoppm) | PDF 转图片 | 额外安装 |
| npm docx 包 | 新建 DOCX | Node.js 全局安装 |
| gcc | soffice.py 编译 C shim | 仅 Linux 需要 |

用户必须安装和配置这些依赖才能正常使用 Office 功能，任何一个缺失或版本不兼容都会导致失败。

#### B. 跨平台兼容性差

Skills 系统的 Python 脚本存在大量 Linux/macOS 假设：

- `recalc.py` 使用 `~/Library/Application Support/` 和 `~/.config/` 查找 LibreOffice 宏目录
- `soffice.py` 编译 C 代码（`LD_PRELOAD` shim），完全不适配 Windows
- `accept_changes.py` 硬编码 `/tmp/` 作为 LibreOffice profile 目录
- 路径分隔符混用（部分脚本用 `/`，部分用 `os.path.join`）

#### C. AI 交互模式天然容易出错

Skills 系统的执行链路：

```
用户请求 → AI 读取 SKILL.md → AI 生成代码/命令 → Bash 执行 → 解析结果 → 可能失败重试
```

每一步都可能出错：
1. **SKILL.md 理解偏差**：文档很长（docx SKILL.md ~480 行），AI 可能遗漏关键步骤
2. **代码生成错误**：AI 生成的 Python/JS 代码可能有语法错误、API 用法错误
3. **XML 编辑错误**：docx 编辑需要直接修改 OOXML，AI 经常生成无效 XML
4. **多轮交互开销**：AI 需要先读文档、再生成代码、再执行、再解析结果——至少 3-4 轮工具调用
5. **缺乏结构化反馈**：Bash 返回的 stdout/stderr 是非结构化文本，AI 需要自行解析错误信息

#### D. 代码重复和维护负担

`.config/skills/docx/scripts/office/` 和 `.config/skills/xlsx/scripts/office/` 包含完全相同的文件：
- `validators/base.py`、`validators/docx.py`、`validators/pptx.py`、`validators/redlining.py`
- `helpers/__init__.py`、`helpers/merge_runs.py`、`helpers/simplify_redlines.py`
- `pack.py`、`unpack.py`、`soffice.py`、`validate.py`

任何 bug 修复都需要同步两份副本。

### 1.3 OfficeCLI 详细评估

#### 工具来源

OfficeCLI 是一个真实的、成熟的开源项目：
- **GitHub**: https://github.com/iOfficeAI/OfficeCLI
- **语言**: C# (.NET 10)，自包含原生二进制（无需安装 .NET 运行时）
- **协议**: Apache 2.0
- **安装**: `irm https://raw.githubusercontent.com/iOfficeAI/OfficeCLI/main/install.ps1 | iex` 或 `winget install HaiYing.OfficeCLI`
- **平台**: Windows x64/ARM64, macOS Apple Silicon/Intel, Linux x64/ARM64

#### 核心架构（三层递进）

| 层级 | 用途 | 命令 |
|------|------|------|
| **L1: 读取** | 语义视图 | `view`（text/outline/annotated/stats/issues/html） |
| **L2: DOM** | 结构化元素操作 | `get`、`query`、`set`、`add`、`remove`、`move`、`swap` |
| **L3: Raw XML** | 直接 XPath 访问 | `raw`、`raw-set`、`add-part`、`validate` |

#### 功能覆盖

| 功能 | Word | Excel | PowerPoint |
|------|------|-------|------------|
| 创建 | ✅ | ✅ | ✅ |
| 读取（多视图） | ✅ | ✅ | ✅ |
| 元素级编辑 | ✅ | ✅ | ✅ |
| CSS 选择器查询 | ✅ | ✅ | ✅ |
| 批量操作 | ✅ | ✅ | ✅ |
| 模板合并 | ✅ | ✅ | ✅ |
| Schema 验证 | ✅ | ✅ | ✅ |
| 实时预览 | - | ✅ | ✅ |
| 公式 | - | ✅ 150+ 内置函数 | - |
| 图表 | ✅ | ✅ 含箱线图/帕累托 | ✅ |
| 数据透视表 | - | ✅ | - |
| 修订追踪 | ✅ | - | - |
| 批注 | ✅ | ✅ | ✅ |
| 图片 | ✅ PNG/JPG/GIF/SVG | ✅ | ✅ 含填充模式 |
| RTL/国际化 | ✅ | ✅ | ✅ |
| 动画/过渡 | - | - | ✅ morph |
| 3D 模型 | - | - | ✅ .glb |
| MCP 服务器 | ✅ 内置 | ✅ 内置 | ✅ 内置 |

#### AI Agent 友好性

OfficeCLI **专门为 AI Agent 设计**，具备以下关键特性：

1. **确定性 JSON 输出**：所有命令支持 `--json`，返回结构化数据
2. **路径寻址**：`/slide[1]/shape[2]` 式路径，无需理解 XML 命名空间
3. **自我修复工作流**：错误返回建议和有效值范围，AI 可自动纠正
4. **渐进复杂度**：L1 简单读取 → L2 DOM 操作 → L3 原始 XML，按需升级
5. **内置帮助**：`officecli pptx set shape.fill` 可查询具体属性格式
6. **原子批量操作**：`batch` 命令支持多操作在一次 open/save 中完成

错误示例：
```json
{
  "success": false,
  "error": {
    "error": "Slide 50 not found (total: 8)",
    "code": "not_found",
    "suggestion": "Valid Slide index range: 1-8"
  }
}
```

### 1.4 对比总结

| 维度 | Skills 系统 | OfficeCLI |
|------|------------|-----------|
| **依赖** | 10+ 个包（Python/Node/LibreOffice/pandoc/gcc） | 单个二进制文件 |
| **安装体积** | >500MB（含 LibreOffice） | ~30MB |
| **跨平台** | 差（大量 Linux 假设） | 优秀（Win/Mac/Linux 全支持） |
| **AI 交互** | 3-4 轮（读文档→生成代码→执行→解析） | 1 轮（直接函数调用） |
| **错误处理** | 非结构化文本输出，AI 需自行解析 | 结构化 JSON 错误 + 建议值 |
| **XML 正确性** | AI 生成 XML，容易出错 | 内部处理，AI 无需接触 XML |
| **功能覆盖** | 基础 CRUD + 部分 LibreOffice 功能 | 全面（公式/图表/透视表/3D/动画/RTL） |
| **可维护性** | 多语言脚本，代码重复 | 单一二进制，零维护 |
| **Token 消耗** | 高（SKILL.md 480 行 + 生成的代码） | 低（结构化参数） |
| **离线能力** | 需要预装所有 Python 包 | 单个 .exe 即可 |
| **更新** | 需要同步维护多份脚本 | `officecli` 自动更新 |

### 1.5 结论与推荐

**推荐方案：迁移到 OfficeCLI，逐步移除 Skills 系统。**

理由：

1. **专为 AI Agent 设计**：OfficeCLI 的三层架构、JSON 输出、路径寻址、自我修复错误提示，都是为 AI 工具调用场景优化的，远优于让 AI 自己生成代码的方式。

2. **消除 XML 错误的根本原因**：Skills 系统要求 AI 直接编辑 OOXML（docx SKILL.md 明确指示"使用 edit_file 修改 XML"），这是 XML 生成错误的根源。OfficeCLI 的 DOM 层（L2）完全屏蔽了 XML 细节。

3. **显著降低 Token 消耗**：OfficeCLI 的函数调用只需几个参数，而 Skills 系统需要 AI 先读 480 行 SKILL.md，再生成数十行 Python/JS 代码，再通过 Bash 执行。

4. **零依赖、跨平台**：单个二进制文件替代 10+ 个依赖包，消除环境配置问题。

5. **项目中的 OfficeCLITools.ts 已经实现**：10 个工具的封装代码已经写好，只需安装 `officecli` 二进制即可启用。

### 1.6 迁移计划

## 二、模型适配框架评估

### 2.1 当前架构概览

```
前端 (React)
  │ IPC: chat:stream(messages, conversationId)
  ▼
ipc/chat.ts ─── OpenAIClient (axios)
  │                    │
  │                    ▼
  │            POST {baseUrl}/chat/completions (SSE)
  │
  ├─ ContextBuilder → 系统提示词
  ├─ ToolManager → 工具定义 (OpenAI Function Calling 格式)
  └─ 工具执行循环 (while true + tool calls)
```

核心设计：**全部走 OpenAI 兼容 API**，通过代理网关访问不同模型提供商。

### 2.2 发现的问题

#### 问题 1：单一客户端承担所有提供商的差异

`OpenAIClient` 硬编码了 OpenAI 的 SSE 格式、请求体结构、错误码语义。当接入非 OpenAI 兼容的 API 时，以下差异无法优雅处理：

| 差异项 | OpenAI | Anthropic (原生) | 阿里通义 (部分) |
|--------|--------|------------------|-----------------|
| 工具调用格式 | `delta.tool_calls` | `content_block_start/stop` | 基本兼容 |
| 思考内容字段 | 不支持 | `thinking` block | `reasoning_content` |
| 图片格式 | `image_url` | `source.base64` | 兼容 |
| 停止原因 | `finish_reason` | `stop_reason` | 兼容 |
| 错误格式 | `error.message` | 嵌套结构 | 可能不同 |

**建议**：引入 Provider Adapter 模式。

```
LLMClient (interface)
  ├─ OpenAIAdapter     ← 当前逻辑迁移至此
  ├─ AnthropicAdapter  ← 原生 Claude API
  └─ GenericAdapter    ← 兜底，适用于其他兼容 API
```

每个 Adapter 负责：
- 消息格式转换
- 流式响应解析
- 工具调用格式处理
- 错误码映射

#### 问题 2：工具调用串行执行

`ToolManager.executeToolCalls()` 逐个执行工具调用（`for...of` + `await`），当模型一次返回多个独立工具调用时（如同时读取两个文件），延迟会叠加。

```typescript
// 当前：串行
async executeToolCalls(toolCalls: ToolCall[], conversationId?: string): Promise<ToolResult[]> {
  const results: ToolResult[] = [];
  for (const toolCall of toolCalls) {
    const result = await this.executeToolCall(toolCall, conversationId);
    results.push(result);
  }
  return results;
}
```

**建议**：对无依赖关系的工具调用使用 `Promise.allSettled()` 并行执行。

注意：需要识别有依赖关系的工具调用（如 `activate_toolset` 必须在其他工具之前执行），对这类情况仍需串行。

#### 问题 3：`reasoning_content` 处理过于简单

当前对思考内容（`reasoning_content`）的处理是直接 `yield` 为普通文本，与正文混在一起：

```typescript
if (reasoningContent) {
  yield reasoningContent;  // 与普通内容一样 yield
}
```

问题：
- 前端无法区分"思考过程"和"正式回复"
- 不同模型的思考内容字段名不同（Qwen: `reasoning_content`，DeepSeek: `reasoning_content`，Claude: `thinking` block），未来无法统一处理

**建议**：使用特殊前缀或结构化格式标记思考内容，前端可以据此展示可折叠的"思考过程"区域。

#### 问题 4：无重试机制

API 调用失败后直接抛出错误，不进行任何重试。对于 429（限流）、502/503（服务暂时不可用）等可恢复错误，应该有自动重试。

**建议**：实现带指数退避 + 抖动的重试机制。

#### 问题 5：模型能力检测过于静态

`capabilityDetector.ts` 使用关键词匹配模型名称来判断能力，存在以下问题：

- 新模型发布后需要手动更新关键词列表
- 无法检测实际的 API 能力（某些代理网关可能不支持特定功能）
- `toolUse` 和 `streaming` 始终为 `true`，但实际有些模型不支持

**建议**：
1. 改为"白名单 + 探测"模式：首次连接时通过 API 测试实际能力
2. 允许用户手动覆盖能力标记

#### 问题 6：`getDefaultMaxTokens()` 硬编码过时

这个方法中的许多值已经不准确（如 GPT-4 默认 8192、Qwen3-8b 仅 8192）。更重要的是，这个值应该从 API 的 `/models` 端点动态获取，而非硬编码。

**建议**：移除整个 `getDefaultMaxTokens()` 方法，改为：
1. 优先使用 `/models` 端点返回的上下文窗口信息
2. 其次使用用户在配置中手动设置的 `maxTokens`
3. 最后兜底使用一个保守的默认值（如 4096）

#### 问题 7：流式解析的健壮性不足

SSE 解析器在以下边界情况下可能出错：

- 多行 JSON 数据（某些代理网关可能会合并或拆分 data 行）
- 非标准 SSE 格式（如 `data:` 前面有空格）
- 超大 JSON 行（工具调用的 arguments 可能很长）

**建议**：
- 增加对不完整 JSON 的容错处理
- 对工具调用 arguments 的增量拼接增加长度限制和校验

### 2.3 双工具系统冗余

项目中存在两套工具管理接口：

| 接口 | 文件 | 使用场景 |
|------|------|----------|
| `Tool` (plain object) | `ToolManager.ts` | 主聊天流（`chat.ts`） |
| `ITool` (class methods) | `core/types.ts` | AgentLoop（未使用） |
| `ToolAdapter` | `core/adapters.ts` | 两者互转 |

`AgentLoop.ts` + `ToolRegistry.ts` + `adapters.ts` 构成了一套 nanobot 风格的工具系统，但在主流程中**完全没有使用**。这是明显的死代码。

**建议**：
- 短期：删除 `AgentLoop.ts`、`ToolRegistry.ts`、`adapters.ts`
- 长期：如果未来需要恢复 nanobot 模式，再重新引入

## 三、其他需要改进的问题

### 3.1 消息 ID 生成方式

```typescript
id: `assistant-${Date.now()}-${Math.random().toString(36).substr(2, 9)}`
```

在高频工具调用循环中，`Date.now()` 可能返回相同值（毫秒精度），导致 ID 冲突。

**建议**：使用递增计数器确保唯一性。

### 3.2 工具结果的序列化方式

```typescript
messages.push({
  role: 'tool',
  tool_call_id: result.toolCallId,
  content: safeStringify(result),  // 整个 ToolResult 被 JSON.stringify
});
```

将整个 `ToolResult`（包括 `success`、`name`、`toolCallId`）都序列化进 `content` 字段，模型只需要看到 `result` 或 `error` 部分，重复信息浪费 token。

**建议**：

```typescript
messages.push({
  role: 'tool',
  tool_call_id: result.toolCallId,
  content: result.success
    ? safeStringify(result.result)
    : `Error: ${result.error}`,
});
```

### 3.3 工具失败警告注入方式

当工具失败 3 次时，注入了一对 `user` + `assistant` 消息。问题：
- 伪造用户消息和 AI 回复，可能导致模型困惑
- 这些消息会被保存到数据库，污染对话历史

**建议**：使用 `system` 消息代替，或者在返回给前端前过滤掉这些注入消息。

### 3.4 上下文窗口管理缺失

当前没有自动的消息截断或压缩机制。当对话变长时：
- 所有历史消息都被发送给模型
- 只有一个简单的 token 计数估算，没有实际的截断动作
- 工具调用的消息（包含大量工具结果）会快速膨胀上下文

**建议**：
1. 实现滑动窗口：保留最近 N 轮对话 + 系统提示词
2. 对早期对话进行摘要压缩（已有 `SessionSummarizer`，但未集成到主聊天流）
3. 对工具结果进行更激进的截断

### 3.5 安全性

#### API Key 存储

API Key 以明文存储在 `electron-store` 的 `config.json` 中。建议使用 Electron 的 `safeStorage` API 加密存储。

### 3.6 错误信息中英混杂

API 错误消息直接透传英文，但用户界面是中文。应该对常见错误进行中文映射。

### 3.7 日志过于冗长

`chat.ts` 中有大量的 `console.log` 调试日志。生产环境应使用日志级别控制。

## 五、架构演进建议

### 当前架构

```
OpenAIClient (单一)
  │
  ├─ 硬编码 OpenAI SSE 格式
  ├─ 硬编码模型 token 限制
  ├─ 无重试、无降级
  └─ 工具调用串行执行

Office 功能：
  AI 读 SKILL.md → 生成 Python/JS 代码 → Bash 执行 → 解析输出
```

### 建议的目标架构

```
LLMClient (interface)
  │
  ├─ OpenAIAdapter
  │   ├─ 消息格式转换
  │   ├─ SSE 解析
  │   └─ 错误码映射
  │
  ├─ AnthropicAdapter (可选，未来)
  │   ├─ Messages API 格式
  │   ├─ SSE 解析（content_block）
  │   └─ thinking block 处理
  │
  └─ GenericAdapter (兜底)
      ├─ 标准 OpenAI 兼容格式
      └─ 通用错误处理

LLMClientFactory
  ├─ 根据 config.provider 自动选择 Adapter
  └─ 支持运行时切换

RetryMiddleware
  ├─ 指数退避 + 抖动
  └─ 可配置重试策略

ToolExecutor
  ├─ 依赖分析（自动识别可并行的调用）
  ├─ 并行执行无依赖工具
  └─ 结果缓存（相同参数不重复调用）

Office 操作：
  AI 直接调用 office_* 工具 → officecli 二进制执行 → JSON 结果
```

核心原则：**将差异封装在 Adapter 层，上层代码只依赖统一的接口**。Office 操作从"AI 生成代码执行"变为"AI 调用结构化工具"。

## 六、总结

### 关键结论

1. **Office 方案：迁移到 OfficeCLI**
   - OfficeCLI 是一个专为 AI Agent 设计的成熟开源工具，单个二进制文件替代 10+ 依赖
   - Skills 系统的"AI 生成代码执行"模式天然容易产生 XML 错误和环境问题
   - 项目中已有完整的 `OfficeCLITools.ts` 封装，只需安装二进制即可启用

2. **模型适配：需要引入 Adapter 层**
   - 当前 `OpenAIClient` 硬编码 OpenAI 格式，扩展性差
   - 建议引入 Provider Adapter 模式，按需支持不同提供商

3. **工具系统：需要清理死代码和优化执行**
   - 删除未使用的 AgentLoop/ToolRegistry/adapters
   - 工具调用并行化、结果序列化优化
   - 工具失败通知改用 system 消息

### 建议执行顺序

1. **先做 P0**（安装 OfficeCLI + 清理死代码）—— 立即改善 Office 功能体验
2. **再做 P1**（移除 Skills + 工具优化）—— 巩固基础
3. **然后 P2**（Provider Adapter + 上下文管理）—— 提升架构能力
