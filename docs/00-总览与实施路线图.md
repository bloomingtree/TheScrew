## 二、已确认的技术决策

根据调研结果，更新以下关键决策：

| 决策项 | 方案 | 说明 |
|--------|------|------|
| **OCR 服务** | **MinerU** `/file_parse` API | 用户已部署，HTTP 接口，multipart/form-data 上传文件 |
| **PDF 解析优先级** | pypdf(文本) → MinerU(扫描件/复杂排版) | 分层 fallback |
| **文档格式** | 以 **Word (.docx)** 为主，含文字+图片 | python-docx 提取文字，图片保存到临时目录 |
| **Windows Server 2012** | **WinRM** + SSH(Skill) 双模式 | 2012 无 OpenSSH，WinRM 作为工具，SSH 作为 Skill |
| **内网镜像** | 用户已有 nginx 搭建的 PyPI 镜像 | 需补充 Python 3.8 对应的包 |
| **多 Agent 协作** | Supervisor 模式（借鉴 DeerFlow） | 主 Agent 分配任务给子 Agent，子 Agent 上下文隔离 |
| **工具次数限制** | 单工具/总工具次数阈值，超出自动中断 | 可配置，默认单工具 10 次，总计 50 次 |
| **工具调用 UI 状态** | 新增 "正在编写工具调用" 状态 | 工具框出现后立即显示状态标签 |
| **Think 检测** | 修复工具调用前的 think 内容归入思考组件 | 确保 `\x01THINKING\x02` 在 tool_call 阶段也能正确展示 |

## 三、MinerU API 集成规格

### 接口信息

| 项目 | 值 |
|------|-----|
| 接口地址 | `http://{host}:{port}/file_parse` |
| 方法 | `POST` |
| Content-Type | `multipart/form-data` |
| 支持格式 | PDF、JPG、PNG（扩展名必须小写） |

### 请求参数

```
POST /file_parse HTTP/1.1
Content-Type: multipart/form-data

参数：
  files          必填    上传文件（PDF/图片）
  backend        可选    "pipeline"（默认，推荐）
  parse_method   可选    "auto"(默认) | "ocr"(强制OCR) | "txt"(纯文本)
  return_md      可选    true（默认，返回 Markdown）
  return_images  可选    false（是否返回提取的图片）
  return_content_list  可选  false
  formula_enable 可选    true（公式识别）
  table_enable   可选    true（表格识别）
  start_page_id  可选    0（起始页）
  end_page_id    可选    99999（结束页）
  lang_list      可选    ["ch"]（语言）
```

### 调用示例

```bash
# 同步解析 PDF，返回 Markdown
curl -X POST http://192.168.1.100:8900/file_parse \
  -H "Accept: application/json" \
  -F "files=@/path/to/doc.pdf" \
  -F "return_md=true" \
  -F "return_images=true"
```

### 集成到 read_file

```typescript
// 当 read_file 检测到 PDF 文件时：
// 1. 先用 pypdf 提取文本
// 2. 如果文本量 < 阈值（可能是扫描件），调用 MinerU
// 3. MinerU 返回 Markdown + 图片引用

async function parsePDF(filePath: string): Promise<FileReadResult> {
  // Step 1: pypdf 快速提取
  const text = await pypdfExtract(filePath);

  if (text.length > 100) {
    // 文本型 PDF，直接返回
    return { fileType: 'pdf', content: text };
  }

  // Step 2: 扫描件，调用 MinerU
  const formData = new FormData();
  formData.append('files', createReadStream(filePath));
  formData.append('return_md', 'true');
  formData.append('return_images', 'true');
  formData.append('parse_method', 'ocr');

  const response = await fetch(`${mineruEndpoint}/file_parse`, {
    method: 'POST',
    body: formData,
  });

  const result = await response.json();
  // result.md_content → Markdown 文本
  // result.images → 提取的图片列表

  return {
    fileType: 'pdf',
    content: result.md_content,
    images: result.images?.map(img => ({
      ref: img.ref,
      path: img.local_path,
      description: img.description,
    })),
  };
}
```

## 四、Windows Server 2012 远程操作方案

### 问题

Windows Server 2012 **没有内置 OpenSSH Server**（OpenSSH 从 Win2019 才内置）。

### 方案：双模式

```
┌─────────────────────────────────────────────────┐
│              远程操作路由                          │
│                                                   │
│  检测目标 OS 版本                                  │
│       │                                           │
│  ┌────┴──────────────────┐                        │
│  │                       │                        │
│  Win2019+               Win2012/2016              │
│  │                       │                        │
│  SSH 工具               WinRM 工具                │
│  (paramiko)             (pywinrm)                 │
│  │                       │                        │
│  └────┬──────────────────┘                        │
│       │                                           │
│  通用远程操作接口                                  │
│  remote_exec(host, command, os?)                   │
└─────────────────────────────────────────────────┘
```

#### 工具 1：`remote_exec`（统一入口）

```typescript
{
  name: 'remote_exec',
  description: '远程执行命令（自动选择 SSH 或 WinRM）',
  parameters: {
    type: 'object',
    properties: {
      host: { type: 'string', description: '服务器地址或资产ID' },
      command: { type: 'string', description: '要执行的命令' },
      // SSH 参数
      port: { type: 'number', description: 'SSH 端口（Linux/Win2019+）' },
      user: { type: 'string', description: '用户名' },
      // WinRM 参数
      auth: { type: 'string', enum: ['ntlm', 'basic', 'kerberos'] },
      // 如果服务器资产中已配置，user/auth 可省略
    },
    required: ['host', 'command']
  }
}
```

#### 工具 2：SSH 作为 Skill（用户建议）

将 SSH 操作封装为 Skill（`.config/skills/ssh/SKILL.md`），而非纯工具：

```yaml
---
name: ssh-ops
type: on-demand
keywords: [ssh, 远程, 连接, Linux]
triggers:
  keywords: [ssh, 远程连接, Linux操作]
---

# SSH 远程操作技能

## 使用说明
通过 Python paramiko 库建立 SSH 连接，支持：
- 执行远程命令
- 上传/下载文件
- 端口转发

## 依赖
- Python 3.8+（已内嵌）
- paramiko（需安装，自动从内网镜像下载）

## 安全提示
- 所有操作记录审计日志
- 危险命令需要用户确认
- 凭证存储在加密的 CredentialStore 中
```

```bash

```

```powershell

winrm set winrm/config/service '@{AllowUnencrypted="true"}'  # 内网可用
```

## 五、UI 改进方案

详见 [05-UI改进与多Agent协作](05-UI改进与多Agent协作.md)，核心改动：

### 5.1 工具调用状态 UI

**问题**：当前模型在编写工具调用参数时，UI 卡住无反馈。工具框已出现但无状态指示。

**解决方案**：在流式解析中新增 `tool_call_writing` 状态

```
流式阶段：
  LLM 开始输出 tool_calls → 前端检测到 tool_call delta
  → 立即显示工具调用框，状态标签："正在编写 tool_call..."

  LLM 完成工具参数 → backend 发送 chat:tool_calls
  → 状态标签切换："正在执行..."

  工具执行完成 → backend 发送 chat:tool_complete
  → 状态标签切换："已完成 ✅"
```

### 5.2 Think 内容归位

**问题**：工具调用前的 think 内容（`\x01THINKING\x02`）没有正确显示在思考组件中。

**根因**：当模型在同一轮回复中先输出 thinking 再输出 tool_calls 时，thinking 内容确实被 `accumulatedThinking` 捕获并存入消息的 `thinkingContent` 字段。但 `AssistantMessage` 组件在渲染时，如果有 tool_calls，可能跳过 thinking 的展示。

**修复**：确保 `AssistantMessage` 组件在有 tool_calls 时也渲染 `thinkingContent`。

### 5.3 工具执行次数限制

**问题**：当前主聊天循环是 `while(true)` 无限制，可能导致无限循环。

**方案**：

```typescript
// electron/main/ipc/chat.ts 修改
const MAX_TOTAL_TOOL_CALLS = 50;    // 单次对话总工具调用上限
const MAX_SINGLE_TOOL_CALLS = 10;   // 单个工具调用上限
const toolCallCounter = new Map<string, number>(); // 按工具名计数
let totalToolCalls = 0;

while (true) {
  // ... 现有逻辑 ...

  if (hasToolCalls) {
    for (const call of toolCalls) {
      totalToolCalls++;

      // 总次数检查
      if (totalToolCalls >= MAX_TOTAL_TOOL_CALLS) {
        // 注入系统消息，告知 LLM 已达上限，要求总结
        messages.push({
          role: 'system',
          content: `工具调用总次数已达上限（${MAX_TOTAL_TOOL_CALLS}次），请立即总结当前结果并回复用户。`
        });
        break;
      }

      // 单工具次数检查
      const toolCount = (toolCallCounter.get(call.name) || 0) + 1;
      toolCallCounter.set(call.name, toolCount);
      if (toolCount >= MAX_SINGLE_TOOL_CALLS) {
        // 发出警告但不中断，给 LLM 一次机会总结
        messages.push({
          role: 'system',
          content: `警告：工具 "${call.name}" 已调用 ${toolCount} 次，请检查是否有更高效的方式。`
        });
      }
    }
  }
}
```

## 六、多 Agent 协作（DeerFlow 模式）

详见 [05-UI改进与多Agent协作](05-UI改进与多Agent协作.md)，核心设计：

### 6.1 Supervisor 架构

```
用户请求 → 主 Agent（Supervisor）
              │
              ├── 分析任务，生成执行计划
              │
              ├── 分配子任务给专门 Agent
              │   ├── devops Agent → SSH 检查服务器
              │   ├── default Agent → 搜索本地运维文档
              │   └── office Agent → 生成故障报告
              │
              ├── 收集结果，综合分析
              │
              └── 生成最终回复
```

### 6.2 与现有 SubagentManager 的关系

当前 `SubagentManager` 已有基础能力（后台 LLM 任务），增强方向：
- 子 Agent 可指定工具白名单
- 子 Agent 结果可流式返回
- 子 Agent 之间上下文隔离但可通过 Supervisor 传递信息
- 增加迭代上限（已有 5 次，保持）

## 七、Python 3.8 内网镜像准备

### 7.1 需要补充的包

用户当前 nginx 镜像有 Python 3.1.1 相关包，需要补充 Python 3.8.10 兼容版本：

```txt
# 运维场景所需包（Python 3.8 兼容版本）
paramiko==2.12.0          # SSH 连接
bcrypt==4.0.1             # paramiko 依赖
cryptography==41.0.7      # paramiko 依赖
pynacl==1.5.0             # paramiko 依赖
pywinrm==0.4.3            # WinRM（需测试 3.8 兼容性）
requests_ntlm==1.2.0      # pywinrm 依赖
requests==2.31.0          # 基础 HTTP
```

### 7.2 下载脚本

```bash
#!/bin/bash
# 在有公网的机器上执行，下载到本地目录
DEST="/data/pypi-packages"

mkdir -p "$DEST"

pip download -d "$DEST" \
  paramiko==2.12.0 \
  bcrypt==4.0.1 \
  cryptography==41.0.7 \
  pynacl==1.5.0 \
  pywinrm==0.4.3 \
  requests_ntlm==1.2.0 \
  requests==2.31.0 \
  --python-version 38 \
  --platform win_amd64 \
  --only-binary=:all:

# 如果某些包没有 wheel，下载源码
pip download -d "$DEST" \
  pywinrm==0.4.3 \
  --no-deps
```

然后将下载的文件放入 nginx 镜像目录，按包名建子目录。
